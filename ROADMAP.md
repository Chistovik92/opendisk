# Дорожная карта OpenDisk

Открытый кроссплатформенный клиент виртуальных облачных дисков (аналог Disk-O / Air Explorer),
без подписок, на движке [rclone](https://rclone.org/) с собственным GUI.

Реализацию ведёт Claude по запросам [[SecretHero]](https://github.com/Chistovik92) —
каждый этап оформляется отдельными PR/коммитами с рабочим кодом, а не только описанием.

## Принцип архитектуры

Диски выглядят как обычные физические (буква диска в Windows, том в Finder, папка в
файловом менеджере Linux, источник в «Файлах» на Android/iOS), но полностью виртуальны:
содержимое не хранится на устройстве, а подгружается по требованию из облака.

Десктоп и мобильные платформы устроены принципиально по-разному — у Android/iOS нет
доступа к FUSE/WinFsp без root/jailbreak, вместо этого у них есть свои официальные
API именно для облачных дисков. Поэтому архитектура состоит из общего ядра и разных
"обвязок" под каждую платформу:

```
                         ┌──────────────────────────┐
                         │      rclone (Go)           │  общее ядро для ВСЕХ платформ:
                         │  протоколы облаков, OAuth,  │  протоколы, кэш, шифрование —
                         │  кэш, шифрование            │  ничего не пишем заново
                         └─────────────┬────────────┘
                                       │
            ┌──────────────────────────┼──────────────────────────┐
            │ Десктоп (Win/Linux/macOS) │      Мобильные (Android/iOS)          │
            │ rclone rcd как процесс,   │      rclone-core собран как           │
            │ GUI общается по HTTP RC   │      библиотека через gomobile        │
            │ API                        │      (.aar / .framework)              │
            └──────────────┬────────────┘      └──────────────┬─────────────────┘
                           │                                    │
        ┌──────────────────▼──────────────────┐   ┌────────────▼─────────────────┐
        │  Виртуальная ФС уровня ОС             │   │  Официальный API облачных     │
        │  Linux: FUSE                           │   │  дисков платформы              │
        │  macOS: macFUSE                        │   │  Android: DocumentsProvider    │
        │  Windows: WinFsp                       │   │  iOS: File Provider Extension  │
        │  → виден ЛЮБОМУ приложению в ОС        │   │  → виден в «Файлах», доступен   │
        │                                         │   │    приложениям через системный │
        │                                         │   │    диалог выбора файла         │
        └─────────────────────────────────────────┘   └─────────────────────────────────┘
```

**Важное отличие мобильных платформ:** на десктопе диск монтируется как настоящая
папка, видимая абсолютно всем программам. На Android/iOS так низкоуровнево работать
запрещено самой ОС — вместо этого используется официальный, предназначенный именно
для облачных дисков механизм (так же устроены официальные клиенты Google Drive и
Dropbox на телефонах). Внешне для пользователя разница минимальна — диск так же
виден в «Файлах» с on-demand загрузкой, — но интеграция с произвольными приложениями
идёт не напрямую через ФС, а через системный диалог выбора файлов.

Мы нигде не переизобретаем протоколы облаков и монтирование — за это отвечает rclone
(70+ провайдеров, включая Яндекс.Диск, Mail.ru через WebDAV, Google Drive, S3, Dropbox)
на всех платформах одновременно. Наша задача — GUI/нативная обвязка под каждую ОС,
автозапуск, трей, профили, кэш-политики.

### Что общего у платформ на самом деле

Общий не только rclone, но и наш код поверх него. Разбор ответов RC API — один
класс `RcloneClient` в модуле `rclone-bridge`, а различается только доставка вызова:
на десктопе HTTP до соседнего процесса `rclone rcd`, на Android — функция внутри
процесса через librclone. Всё, что добавляется в этот класс, появляется на всех
платформах сразу; так, ссылки на файлы (0.4.0) писались один раз и на Android
уже работают, хотя интерфейса там ещё нет.

Раньше она была разбита на «этапы» — от них пришлось отказаться: этапы шли не по

на [странице релизов](https://github.com/Chistovik92/opendisk/releases).

намеренно, порядок важнее дат.

## Выпущено

### 0.1.x — рабочий десктоп

Ядро и интерфейс. К концу ветки приложение делало всё, ради чего затевалось.

- **Ядро** `rclone-bridge`: запуск и остановка `rclone rcd`, типизированная
  обёртка над RC API, разбор ошибок rclone в человеческий текст.
- **Встроенный rclone**: едет внутри дистрибутива, скачивается при сборке
  и сверяется по SHA-256. Отдельно ставить ничего не нужно.
- **Интерфейс** на Compose Multiplatform: список облаков, мастер добавления,
  подключение диском, занятое место, трей, уведомления.
- **Плитки популярных сервисов** вместо списка из семи десятков бэкендов;
  полный список остался за «другим подключением».
- **Монтирование**: WinFsp едет в дистрибутиве Windows и ставится по кнопке;
  на Linux `fuse3` прописан в зависимостях пакета.
- **Режимы кэша** — ответ на главный вопрос «скачивать всё или по требованию».
- **Автозапуск, автоподключение, ограничение скорости, русский и английский.**
- **Упаковка**: MSI (свой установщик на WiX — jpackage не умеет закрывать
  работающее приложение), DEB, RPM, AppImage, DMG; сборка в CI на трёх ОС.
- **Установка на Linux одной командой** скриптом с GitHub.
- **Окно «О приложении»**, руководство пользователя, страница проекта.

### 0.2.x — то, что вскрылось при реальной эксплуатации

Ветка целиком состоит из починок, и почти каждая нашлась не по коду, а по жалобе
или замеру на живой системе.

- **0.2.5** — обновление из приложения со сверкой контрольной суммы; уборка
  за собой при удалении, с отдельным спросом про конфиг облаков и WinFsp.
- **0.2.6** — диски на Windows стали сетевыми: как обычные локальные они
  заставляли систему их индексировать, и медленное облако подвешивало
  проводник целиком. Предупреждение про общий идентификатор Google:
  замер на живом диске дал 33 секунды на список из 65 файлов против одной
  секунды у Яндекса.
- **0.2.7** — неверный идентификатор Google ловится до похода в браузер;
  из ожидания подтверждения можно выйти.
- **0.2.8** — поле подключения можно очистить. Без этого нельзя было уйти
  с удалённых учётных данных Google.
- **0.2.9** — rpm собирался неправильно: встроенный rclone был неисполняемым,
  ярлык пропадал после каждого обновления, работающая копия не закрывалась.

Кроме того, в эту же ветку попали починки, каждая из которых была настоящей
поломкой: автозапуск не работал ни в одной версии; на Linux не создавался
каталог точки монтирования; осиротевший rclone после аварийного завершения
держал диски.

### 0.3.x — поставилось и нашлось

- **0.3.0** — галка «Запустить OpenDisk» на последней странице установщика
  Windows, отмеченная по умолчанию; обновление изнутри приложения запускает
  новую версию само; на Linux пакет возвращает приложение, если сам же его
  закрыл ради обновления.
- **0.3.1** — в строке состояния сказано, что сетевой диск лежит в разделе
  «Сетевые расположения». До этого человек открывал «Этот компьютер», среди
  обычных дисков ничего не находил и решал, что диск не смонтировался.

### 0.4.x — ссылки на файлы

Первая возможность, а не починка, за две ветки. Вопрос был простой: файл лежит
на подключённом диске, надо дать на него ссылку — и до сих пор для этого
приходилось идти на сайт сервиса.

- **Ссылку выдаёт то облако, которое файл действительно держит.** Приложение
  раскладывает местный путь (`Z:\Отчёты\март.pdf`) обратно на облако и путь
  внутри него (`яндекс` + `Отчёты/март.pdf`) и просит ссылку у нужного сервиса.
  Диск определяется по самому пути: в файловом диалоге можно уйти на соседний
  подключённый диск, и ссылка придёт от него, а не от того, с чьей кнопки начали.
- **Кнопка есть только там, где ссылки возможны.** Умеет ли бэкенд ссылки,
  спрашивается у самого rclone (`operations/fsinfo`), а не берётся из зашитой
  в код таблицы, которая устаревала бы молча. У Яндекс.Диска, Google Диска,
  Dropbox и OneDrive ссылки есть; у SFTP, FTP и обычного WebDAV их нет в самом
  протоколе — и об этом говорится словами, а не кодом ошибки.
- **Ссылку можно отозвать оттуда же, откуда выдали.** Сделать файл публичным
  легко, и закрыть доступ должно быть так же легко; иначе остаётся только идти
  на сайт сервиса. Файл при этом остаётся на месте.
- **Написано в общем модуле — значит, работает и на Android.** `publicLink`,
  `fsInfo` и разбор пути лежат в `rclone-bridge`, который на телефоне тот же
  самый; инструментальные тесты гоняют их через librclone на эмуляторе.
  Интерфейса на Android пока нет, но ядро возможности уже есть и проверено.

**Неполный релиз больше не может уехать наружу.** Раньше каждая сборка сама
делала релиз видимым, как только доходила до конца, — и релиз становился
публичным от первой успевшей платформы. Теперь релиз создаётся черновиком, а
публикует его отдельная работа после всех трёх сборок сразу и только убедившись,
что в нём есть установщики под каждую платформу. Упала хоть одна — релиз
остаётся черновиком, и пользователи его не видят.

**0.4.1** — тем же выпуском, потому что 0.4.0 доехал только до Windows.
Новые тесты сверяли сообщение об ошибке с русской подстрокой, а язык
интерфейса берётся из системы: на англоязычных раннерах Linux и macOS то же
самое сообщение приходило по-английски, тесты падали и сборка пакетов до
выкладывания не доходила. Сверка теперь идёт с той строкой, которую берёт сам
контроллер, — двуязычие перестало быть ловушкой для тестов.

### 0.5.0 — установщик под каждую машину

Выпуск целиком про упаковку: приложение то же, а вот получить его должно быть
одинаково просто на любой машине.

- **На Windows теперь `.exe`, а не `.msi`.** MSI никуда не делся — он уехал
  внутрь exe: вся выстраданная логика установщика (закрытие работающего
  приложения при обновлении, стабильные GUID-ы компонентов, уборка при
  удалении) осталась в нём, переписывать её ради смены расширения было бы
  напрасным риском. Снаружи — привычный установщик, который и Windows, и
  браузеры встречают спокойнее, чем MSI.
- **Windows под ARM.** Отдельный `.exe` для ноутбуков на ARM: своя JDK, свой
  rclone, своя сборка. Раньше такие машины могли только эмулировать x64.
- **macOS в двух архитектурах.** Отдельные `.dmg` для Apple Silicon и для
  Intel — до этого собирался один, и какой именно, зависело от того, какой
  раннер сегодня у GitHub.
- **Свой пакет для ALT Linux и Simply Linux.** ALT — не производная Fedora
  и не совместим с ней по именам зависимостей: rpm от jpackage там либо не
  ставился, либо тянул не то. Теперь его собирает контейнер самого ALT.
- **Скрипт установки смотрит на дистрибутив, а не только на пакетный
  менеджер.** Debian и Ubuntu получают `.deb`, ALT и Simply — свой rpm,
  Fedora и openSUSE — свой, всё остальное — AppImage, который не зависит
  ни от какого пакетного менеджера. Выбор проверяется тестом на файлах
  `/etc/os-release` полутора десятков дистрибутивов: живых систем для проверки
  нет и не будет, а их os-release известен.
- **Android: приложение, а не только ядро.** Список облаков с занятым местом,
  добавление облака логином и паролем, просмотр по папкам, ссылка на файл —
  всё на общем с десктопом коде. В релизе два `.apk`: под arm64 и
  универсальный. Диска в системном «Файлы» пока нет — это `DocumentsProvider`,
  и он в 0.6.

**Что «все платформы» значит и чего не значит.** Установщики теперь есть под
Windows (x64 и ARM), Linux (deb, два rpm, AppImage), macOS (Intel и Apple
Silicon) и Android. Под iOS установщика нет и в этом выпуске быть не может:
файл, который ставится на iPhone, обязан быть подписан сертификатом Apple,
а сертификат выдаётся только участнику платной программы разработчика.
Это не техническая задача и обходится не кодом. Собрано и проверено то, что
собрать можно: ядро rclone под iOS (`.xcframework`, устройства и симулятор).

**0.5.2 — то, что 0.5.0 сломал молча, и проверка, которая этого больше не
допустит.** Переход на `.exe` сломал две вещи, о которых узнать было
неоткуда: встроенное обновление искало `.msi` и перестало ставить что-либо,
а удаление изнутри приложения сносило скрытый MSI и оставляло в «Программах
и компонентах» запись-сироту. Сценарии установки и удаления вынесены в файлы,
и CI гоняет ровно их на настоящей Windows — x64 и ARM: старый `.msi` →
прошлый `.exe` → обновление запущенного приложения → запуск → удаление.
Linux-пакеты перед выпуском ставятся тем самым `install.sh` в чистых Debian,
Ubuntu 22.04 и 24.04, Fedora, openSUSE и ALT, с обновлением с прошлой версии.
Там же нашлись и исправлены пакет ALT, который требовал не тот FUSE и вёз
неисполняемый rclone, и Android — пароль без маски, облако нельзя было
удалить, код версии навсегда оставался единицей.

## Дальше

### 0.6 — Android и iOS вместе

Обе мобильные платформы делаются одной веткой, а не по очереди. Причина не в
удобстве планирования: у них общее всё, кроме нативной обвязки, — тот же rclone,
тот же `RcloneClient`, тот же разбор путей. Делать их по очереди означало бы
дважды проходить одну и ту же дорогу.

Что уже готово:

- [x] Сборка `rclone` под Android через `gomobile bind` в CI, с публикацией
      библиотеки отдельным релизом и сверкой по SHA-256.
- [x] Транспорт поверх librclone; разбор ответов RC API общий с десктопом.
- [x] Инструментальные тесты на эмуляторе — включая ссылки на файлы (0.4.0).

Android — приложение выпущено в 0.5.0, осталось главное:

- [x] Интерфейс на Compose: облака, добавление, просмотр по папкам.
- [x] Ссылки на файлы — на общем с десктопом коде.
- [x] Раздача с учётом размера: ABI splits, а не один apk на всех.
- [ ] `DocumentsProvider` — официальный и единственный путь для облачных
      дисков на Android. Пока его нет, диск не виден в системном «Файлы»,
      и приложение остаётся отдельным окном, а не диском.
- [ ] Фоновая работа через `WorkManager`, кэш по требованию.
- [ ] Сервисы с подтверждением в браузере: их поток требует вернуть человека
      из браузера обратно в приложение.

iOS:

- [x] Сборка `librclone` в `.xcframework` — отдельным workflow на macOS-раннере,
      как уже сделано для Android, с публикацией библиотеки отдельным релизом
      и сверкой по SHA-256. Сделано первым намеренно: в документации rclone про
      iOS сказано, что gomobile «должен работать», и это никем не проверялось, а
      раннер GitHub — единственный доступный способ узнать ответ. Собирается и
      под устройства (arm64), и под симулятор — без второго ничего нельзя даже
      запустить в Xcode.
- [ ] **File Provider Extension** — официальный и единственный путь у Apple.
- [ ] Интерфейс: SwiftUI либо Compose Multiplatform — решаем по состоянию
      его iOS-таргета на момент старта, а не сейчас.
- [ ] Транспорт поверх `.xcframework`, как `LibrcloneTransport` на Android.
      Разбор ответов при этом остаётся общим — переписывать нечего.

**Почему в релизах нет установщиков под телефоны.** Установщик — это собранное
приложение, а приложений пока нет: есть ядро. У Android это `.apk`, и для него
нужен сам клиент — `DocumentsProvider`, экраны, фоновая работа; собрать пустой
apk можно, но ставить в релиз нечего. У iOS сложнее: `.ipa` без подписи не
существует как формат установки, а подпись требует платной программы
разработчика Apple. То есть на Android установщик появится вместе с
приложением, а на iOS — вместе с оплаченной программой, и раньше никак.

**Два условия входа, которые не решаются кодом.** Про них лучше знать заранее,
чем упереться в них на середине:

1. **Платная программа разработчика Apple.** Без неё приложение не поставить
   даже себе больше чем на неделю, а в App Store — никак. Это не техническая
   задача, и обойти её нечем.
2. **Mac для проверки.** Собрать `.xcframework` и приложение можно на раннере
   GitHub, а вот запустить и посмотреть — нет. Ровно та же история, что с
   `.dmg`: он собирается каждый выпуск с самого начала и **ни разу никем не
   запускался**.

**Ограничение платформы, а не недоделка:** диск не будет виден произвольной
программе как папка ни на Android, ни на iOS. Обе системы такого не позволяют
никому, включая официальные клиенты Google Drive и Dropbox.

### 0.7 — то, что мешает пользоваться

Накопилось за время эксплуатации десктопа и никуда не делось.

- [ ] **Диагностика медленного облака.** Сейчас «тормозит» выясняется только

## Потом

- Шифрование содержимого на лету — у rclone это готовый бэкенд `crypt`.
- Синхронизация по расписанию, а не только монтирование по требованию.
- Срок жизни у ссылок: rclone умеет `expire`, и в API это уже проброшено —
  нужен способ задать его в интерфейсе, не превращая кнопку в форму.
- Общий слой бизнес-логики между десктопом и мобильными. Сейчас общие разбор
  ответов RC API и работа со ссылками; объединять остальное имеет смысл после
  того, как мобильные таргеты устоятся.
- Плагины для бэкендов, которых нет в rclone.

## Чего в карте нет намеренно

- **32-битные сборки.** Движок отрисовки под x86 не выпускается, а 32-битных
  JDK новее восьмой версии не существует.
- **Свой протокол или свой клиент облаков.** Всё это делает rclone, и делает
  лучше, чем получилось бы у нас.
- **Свой сервис коротких ссылок.** Ссылку на файл выдаёт сам сервис, у которого
  файл лежит, — только у него есть публичный адрес и только он отвечает за
  доступ к нему. Своя прослойка означала бы свой сервер, свои расходы и свою
  ответственность за чужие файлы.
- **Сроки.** Порядок важнее: каждый выпуск этой ветки появлялся из того,
  что нашлось при использовании, а не из плана.
